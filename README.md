# ITP ТОИР · Backend

Автономный Laravel 12 API для системы технического обслуживания и ремонта. **Portal/HRM/Inventory не нужны для входа.** Учётные данные хранятся только в базе ТОИР. Не копируйте .env или базы данных других проектов.

## Запуск

1. Требования: PHP >= 8.2, Composer, SQLite (для локального режима) либо отдельная PostgreSQL/MySQL БД.
2. \`composer install\`
3. Скопировать \`.env.example\` в \`.env\`. В production: \`APP_ENV=production\`, \`APP_DEBUG=false\`, \`APP_URL\` и \`TOIR_FRONTEND_URL\` с HTTPS, \`SESSION_SECURE_COOKIE=true\`, настроить SMTP и изолированную БД.
4. \`php artisan key:generate\`
5. Для SQLite создать \`database/database.sqlite\` (или указать \`DB_DATABASE\`).
6. \`php artisan migrate\`
7. \`php artisan toir:bootstrap --email=admin@example.test --name="Администратор" --company="ITP Mining" --code=itp-mining\` (пароль вводится скрыто, на экране и в аргументах процесса не появляется).
8. \`php artisan serve --host=127.0.0.1 --port=8000\`
9. \`php artisan test\`

В production отдавайте Vue SPA и API из **одного origin**, либо настройте разрешённый first-party CORS/CSRF в рамках собственного домена. Публичной регистрации, демо-паролей или фейковой авторизации нет.

## Авторизация

Сессионная авторизация Laravel с HttpOnly cookie, CSRF, rate limits, восстановлением пароля, сменой пароля и выбором компании. Клиент сначала выполняет GET \`/sanctum/csrf-cookie\`, затем POST \`/api/v1/auth/login\`. Сведения о профиле: GET \`/api/v1/auth/me\`. Смена компании: POST \`/api/v1/auth/companies/switch\`. Выход: POST \`/api/v1/auth/logout\`.

Роли привязаны к компании (owner/admin/manager/engineer/technician/viewer). Активная компания хранится **в сессии**, не в глобальном поле пользователя. Это исключает переключение активной компании в другом браузере той же учётной записи. Проверка роли и tenant context обязательно применяется к будущим CRUD-эндпоинтам.

Письма сброса пароля в local окружении уходят в LOG, в production настройте MAIL_* до включения восстановления.

## Данные

\`users\`, \`companies\`, \`company_user\`, \`sessions\`, \`password_reset_tokens\`, \`toir_audit_events\`. Предметные таблицы оборудования и ремонтов добавляются отдельным этапом после согласования схемы и tenant policy.

## Статус

Основа самостоятельного backend + сессионный вход; без автоматической связи с Portal. В CI и на сервере проверить запуск приложения, миграции и все feature tests до деплоя. Не запускать миграции на чужих БД.


## Приглашение новых сотрудников и подтверждение почты

После настройки реального SMTP администратор создаёт пользователей только через доверенную консоль:

`php artisan toir:invite-user --email=engineer@example.com --name="Инженер" --company-code=itp-mining --role=engineer`

Система выдаёт случайный нераскрываемый пароль и отправляет на указанный адрес одноразовую ссылку для установки собственного пароля. Пользователь не может войти до открытия ссылки и установки пароля; это же действие подтверждает владение адресом почты (`email_verified_at`). Пароль и токен не выводятся в командной строке и не хранятся в журнале аудита. При неудачной отправке существующий аккаунт остаётся неактивированным; повторную ссылку можно запросить через восстановление пароля после исправления SMTP.

Вход администратора, созданного `toir:bootstrap`, разрешён сразу, поскольку его почта отмечается подтверждённой при доверенной первоначальной настройке. Публичной регистрации нет.

В текущей реализации управление приглашениями осуществляется через CLI; административный экран пользователей и гранулярные разрешения для будущих модулей создаются в следующем этапе.


## Первая предметная схема ТОИР

Отдельная миграция \`2026_11_02_010000_create_toir_domain_tables.php\` создаёт:

- \`toir_assets\`: иерархия активов, категории premises/equipment/tools/materials, серийные номера и стоимость.
- \`toir_employees\`: собственный реестр исполнителей.
- \`toir_projects\`: технические проекты и сроки.
- \`toir_work_orders\` и \`toir_work_order_events\`: наряды-задания с изменениями статусов и историей.
- \`toir_maintenance_plans\`: ППР и очередные даты обслуживания.
- \`toir_supplies\`: заявки на материалы и склад.
- \`toir_tenders\`: закупочные инициативы.

Маршруты: \`GET /api/v1/overview\`, \`GET /api/v1/schedule\`, а также \`GET|POST /api/v1/resources/{resource}\` и \`GET|PATCH|DELETE /api/v1/resources/{resource}/{id}\` для \`assets, employees, projects, work-orders, plans, supplies, tenders\`.

Все запросы выполняются только в активной компании **из сессии пользователя**. Поля \`company_id\` и \`id\` не принимаются от клиента; связанные внешние ключи проверяются на принадлежность этой же компании. Роли owner/admin/manager имеют право изменения, engineer изменяет наряды/планы/поставки, viewer и technician сейчас имеют только чтение. Перед расширением прав для technician потребуется бизнес-правило подтверждения работ.

Номера нарядов создаются сервером, изменения записываются в \`toir_work_order_events\`. Физическое удаление не выполняется, используется soft delete. Перенос между категориями, сложные переходы статусов и складские остатки требуют следующего блока работ.

## Восстановление и приглашения

SMTP необходимо настроить отдельно. При транспортных драйверах \`log\` и \`array\` в production запрос восстановления пароля не создаёт отправку фиктивного письма: API показывает недоступность, frontend блокирует форму. Тестовые Laravel Feature тесты проверяют восстановление в окружении \`testing\`. Приглашение \`toir:invite-user\` также заблокировано без реальной отправки в production.

## Развёртывание

Серверный staging изолирован в \`C:\deploy\toir\backend\current\` и \`C:\deploy\toir\site\current\`. **Нельзя** копировать .env или базу из других проектов. Два отдельных Windows-сервиса \`ITP-TOIR-FastCGI\` (127.0.0.1:18122) и \`ITP-TOIR-HTTP\` (127.0.0.1:18120) доступны через единственный префикс \`/toir\` на HTTPS-хосте. Сеансовая cookie именуется \`itp_toir_session\`, \`SESSION_PATH=/toir\`, secure=true, HttpOnly. Временный хост не является SSO Portal.

Развёртывание: \`php artisan migrate --force\` **только на отдельной БД ТОИР после резервного копирования**. На серверах с PostgreSQL обновить независимые параметры подключения и прогнать миграции на копии, прежде чем переключить prod. Включить реальный SMTP и резервное копирование. Не публиковать пароль и APP_KEY в коммитах.

Проверки: \`php artisan test\` (29+ тестов, включая 9 предметных), отдельная HTTP-проверка CSRF и визуальная приёмка.
